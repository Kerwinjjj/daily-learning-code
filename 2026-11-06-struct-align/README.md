# 结构体、结构体指针、内存对齐（Day6 · MCU 必考）

> 以**代码和注释**为主，图表用于**比对**；英文缩写标注中文。

## 0. 一句话总结

| 概念 | 一句话 |
|---|---|
| 结构体 | 把类型不同的变量打包成一条"记录"，内存连续存放 |
| 结构体指针 | 指向整条记录的指针，用 `->` 访问成员 |
| 内存对齐 | 编译器为了访问效率，在成员之间**插入填充字节** |
| `packed` | 取消填充，让字节数与协议格式严格一致 |

## 1. 结构体基础

| | 数组 | 结构体 |
|---|---|---|
| 成员类型 | 必须全相同 | 可以全不同 |
| 访问方式 | `a[i]` 按下标 | `s.name` 按名字 |
| 内存布局 | 紧密排列，无空隙 | **有填充字节**（对齐导致） |
| 典型用途 | 一组同类数据 | 一个设备的完整描述 |

**命名约定：** `typedef struct {...} Device_t;` 中 `_t` 表示"这是一种**类型**"（type 的缩写）；变量名通常取它的缩写，如 `Device_t dev;`。类型名和变量名是两个不同的东西，变量名没有语法约束，只需可读。

```c
typedef struct {
    uint8_t  id;       /* 设备号 */
    uint16_t value;    /* 数值 */
    char     name[8];  /* 名字 */
} Device_t;

Device_t dev = { .id = 1, .value = 250, .name = "motor" };
/*     ↑ 这一行同时完成"声明 + 初始化"，dev 这个名字就从这里诞生 */
```

## 2. 结构体指针：`->` 就是 `(*p).成员` 的简写

| 写法 | 用在什么上 | 等价写法 |
|---|---|---|
| `dev.value` | 结构体**变量** | — |
| `p->value` | 结构体**指针** | `(*p).value` |
| `(*p).value` | 结构体指针（完整写法） | `p->value` |

为什么需要 `->`：`.` 的优先级高于 `*`，`*p.value` 会被解析成 `*(p.value)`，所以必须写 `(*p).value`；每次加括号太麻烦，于是有了 `->`。

**实测（demo1）：**

```
dev.id    = 1, p->id    = 1
dev.value = 250, p->value = 250
p->name   = motor
after p->value = 300, dev.value = 300
offsetof id    = 0
offsetof value = 2
offsetof name  = 4
sizeof(Device_t) = 12
```

两处值得注意：

- `p->value = 300` 之后 `dev.value` 也变成 300 —— 指针和变量指向**同一块内存**；
- `offsetof value = 2`、`sizeof = 12` —— 数据实际只有 1+2+8=11 字节，多出来的是**填充**，这就是对齐。

## 3. 内存对齐：三条规则

| 规则 | 内容 |
|---|---|
| ① 成员偏移 | 每个成员的起始偏移必须是它**对齐数**的整数倍（`uint8_t`=1、`uint16_t`=2、`uint32_t`/`float`=4、`double`=8） |
| ② 结构体总大小 | 必须是**最大成员对齐数**的整数倍，不够在尾部补齐 |
| ③ 结构体自身对齐数 | 等于成员里最大的那个对齐数 |

两处填充的判断依据不同：

| 填充位置 | 依据 |
|---|---|
| 成员之间 | 看**紧跟在后面的那个成员**的对齐要求（不是最大成员） |
| 结构体末尾 | 看**最大对齐数** |

**实测反例（同样是 `char` 后面，填充量从 0 到 7 都有）：**

```
A: sizeof= 8 | a=0 b=4          /* char 后接 int    → 补 3 */
B: sizeof= 8 | a=0 c=1 b=4      /* char 后接 char   → 补 0 */
C: sizeof=16 | a=0 d=8          /* char 后接 double → 补 7 */
D: sizeof= 4 | a=0 b=2          /* char 后接 short  → 补 1 */
```

**口诀：成员之间看"下一个"，末尾看"最大"。**

## 4. 为什么要对齐

| 原因 | 说明 |
|---|---|
| **一次总线访问** | CPU 按字（4/8 字节）读内存，未对齐成员跨字边界要读两次再拼 |
| **正确性** | x86 能自动处理未对齐访问（慢一点）；**ARM Cortex-M 某些未对齐访问直接 HardFault**（硬件错误） |
| **硬件要求** | DMA（直接存储器访问）、外设寄存器要求地址对齐 |
| **缓存行** | 跨 cache line 要两次访存 |

一句话：**对齐是用"浪费几个字节"换"访问速度和硬件正确性"。**

## 5. demo2：同样四个成员，三种排法（实测）

```c
typedef struct { uint8_t a; uint32_t b; uint8_t c; uint16_t d; } Plain_t;      /* 默认对齐 */
typedef struct { uint32_t b; uint16_t d; uint8_t a; uint8_t c; } Reorder_t;    /* 重排顺序 */
typedef struct { uint8_t a; uint32_t b; uint8_t c; uint16_t d; }
        __attribute__((packed)) Packed_t;                                      /* 取消对齐 */
```

**实测（`sizeof` 与成员偏移）：**

| 结构体 | sizeof | a | b | c | d |
|---|---|---|---|---|---|
| `Plain_t`（默认） | **12** | 0 | 4 | 8 | 10 |
| `Reorder_t`（重排） | **8** | 6 | 0 | 7 | 4 |
| `Packed_t`（packed） | **8** | 0 | 1 | 5 | 6 |

三个结论：

1. **默认对齐会插填充**：`a` 后补 3 字节（为了让 `b` 落在 4 的倍数）、`c` 后补 1 字节（为了让 `d` 落在 2 的倍数）；
2. **不改规则也能省空间**：把大成员（`b`、`d`）放前面，填充消失，12 → 8。这是工程里优先做的免费优化；
3. **packed 强制紧排**：`b` 从偏移 1 开始（不再要求 4 的倍数）。

### 逐字节验算 `Plain_t`

| 步骤 | 放谁 | 当前偏移 | 对齐要求 | 补几字节 | 放完 |
|---|---|---|---|---|---|
| 1 | `a`（1 字节） | 0 | 1，0 是倍数 ✓ | 0 | 1 |
| 2 | `b`（4 字节） | 1 | 4，1 不是倍数 ✗ | **补 3** | 4 → 8 |
| 3 | `c`（1 字节） | 8 | 1 ✓ | 0 | 9 |
| 4 | `d`（2 字节） | 9 | 2，9 不是倍数 ✗ | **补 1** | 10 → 12 |
| 5 | 末尾 | 12 | 最大对齐 4，12 是倍数 ✓ | 0 | **12** |

## 6. packed：为什么串口协议必须用（demo3 实测）

```c
typedef struct {
    uint8_t  header;      /* 帧头 0xAA */
    float    angle;       /* 角度 */
    uint16_t checksum;    /* 校验 */
} __attribute__((packed)) UartFrame_t;
```

**实测字节流（模拟串口线上的真实内容）：**

```
sizeof(UartFrame_t)  = 7
packed 帧字节        : AA 00 00 F4 41 34 12

sizeof(NormalFrame_t) = 12
普通帧字节（含填充）  : AA 00 00 00 00 00 F4 41 34 12 00 00
```

`float` 30.5 的机器表示是 `0x41F40000`，小端（低字节在前）存成 `00 00 F4 41`。

| 位置 | packed 版 | 普通版 | 说明 |
|---|---|---|---|
| 0 | `AA` | `AA` | 帧头 |
| 1–3 | `00 00 F4` | `00 00 00` | **普通版这里是填充** |
| 4–6 | 角度剩余 | `00 F4 41` | 角度被挤到偏移 4 |
| 8–9 | — | `34 12` | 校验 |
| 10–11 | — | `00 00` | 尾部补齐 |

**危害：** 你按"帧头 1 + 角度 4 + 校验 2 = 7 字节"设计协议，普通结构体却发出 12 字节、中间夹 3 字节填充。对端从第 2 字节开始读角度 → **读到的全是填充 + 错位 → 角度永远是垃圾值**。

**注意：** 上面的填充字节凑巧是 `00`，那是栈上干净内存；**实际工程里是未定义的内存残留，不能依赖它一定是 0**。

## 7. packed 的弊端与使用场合

| 弊端 | 具体表现 |
|---|---|
| **非对齐访问** | 成员地址不再对齐（`float` 在偏移 1）；x86 能容忍，**ARM Cortex-M 某些未对齐访问直接 HardFault** |
| **取地址受限** | 把 packed 成员的地址传给要求对齐的接口（DMA、外设寄存器）会出问题 |
| **变慢变大** | 编译器可能把一次读改成逐字节读再拼，代码变长、速度下降 |
| **原子操作不可用** | 非对齐成员无法做原子读写 |

| 使用场合 | 例子 |
|---|---|
| 与外部格式严格对应 | 串口帧、网络报文、文件格式、Flash/EEPROM 固定布局 |
| 硬件寄存器映射 | 按芯片手册把寄存器块定义成结构体（地址由芯片定死，绝不能有填充） |
| 内部数据处理 | **不要用**：用默认对齐 + 重排成员顺序更划算 |

语法细节：`__attribute__` 是 **GCC / Clang 扩展**（非标准 C），`((packed))` 是具体指令。跨编译器要换写法：MSVC 用 `#pragma pack(1)`，Keil ARMCC 支持 `__attribute__((packed))` 或 `__packed`。

## 8. 收发的坑：接收端用 memcpy，不要强转指针

```c
/* 发送：把结构体当字节流发出去 */
uart_send((uint8_t *)&frame, sizeof(frame));      /* packed → 正好 7 字节 */

/* 接收：不要写 (UartFrame_t *)rx_buf 直接解析 */
uint8_t rx_buf[64];
/* ... 收满 7 字节 ... */
UartFrame_t f;
memcpy(&f, rx_buf, sizeof(f));                    /* 先拷进来，再按结构体访问 */
```

原因：`rx_buf` 的首地址不一定满足对齐要求，直接强转成结构体指针再访问 `float` 成员，在 ARM 上可能就是非对齐访问 → HardFault。`memcpy` 走字节拷贝，安全。

## 9. 口述题答法

**对齐原因（四层）：** ① CPU 按字访问内存，一次总线读写效率最高 → ② 未对齐成员跨字边界，需要读两次再拼 → ③ 更关键是正确性：ARM 上某些未对齐访问 HardFault，DMA/外设也要求对齐 → ④ 所以编译器插填充字节，用空间换速度和正确性。

**packed 何时用：** 与外部协议严格对应（串口帧、网络包、文件格式）、芯片寄存器映射、Flash/EEPROM 固定布局。**弊端：** 成员不再对齐 → ARM 上可能 HardFault、访问变慢、代码变大；对 packed 成员取地址传给 DMA 等对齐敏感接口会出错；不能用原子操作。
